# 选题可行性探测报告

**对象**：《面向大学生的校园待办中心》选题文稿
**前提**：学校开放平台的接口权限已获批——scope 齐备、客户端模式与授权码模式均可用、推送渠道可发
**探测时间**：2026-11-20 ｜ **环境**：本机公网出口（非校园网），Python 3.12 标准库
**产物**：`probe/probe_feasibility.py`（9 项实测）、`probe/api_inventory.csv`（235 条接口）、`probe/api_catalog.json`（官方目录 237 条）、`probe/key_endpoints.csv`、`probe/probe_result.json`

---

## 0. 一句话结论

**拿到全量接口后，这个选题在结构上很顺**：7 类校内数据可以直接产出结构化待办，日程接口自带重复规则与多渠道提醒，等于把"提醒"这件最容易出事故的事外包给了平台。

真正剩下的硬缺口只有 5 个，且都不阻塞主链路：**没有作业接口**、**官网没有 RSS 且部分正文是 PDF 图片**、**校历接口故障**、**OCR 只收公网 URL**、**提醒准点率以本地调度路径验收**。

## 2. 拿到权限后，数据长什么样（决定功能怎么设计）

以下字段均取自接口文档的返回参数表，不是推测。

### 2.1 课表 `GET /v2/dc/teaching_info/student_timetable`

```
userId 学号 · name 姓名 · year 学年度 · term 学期
courseName 课程名称 · teacherName 教师 · classDeptName 开课学院
weekday 星期 · startUnit 开始节 · endUnit 结束节 · week 周次
classroomName 教室 · campusName 校区 · administrativeClassNo 教学班
delInd 删除标识（退课时置 D）· updateTime
```

**这是本轮最有价值的一条**：它给的是"星期几第几节、哪几周、哪个教室"，不是一段 `classTime` 字符串。意味着：

- 课程维度归类不需要猜——通知正文里出现"数据结构""100165"，直接命中课表
- **可以按 `eventRepeatType=2`（每周）批量写日程**，把"每节课前 15 分钟提醒"变成一次 API 调用
- 增量同步要处理 `delInd='D'`（退课），否则课表会越同步越多

> 注意 `v2` 是 DC（批量/数据中心）版本，字段全但可能非实时；`v1/rt/onetongji/student_timetable` 是实时版本，字段少（`timeTableList` 示例里为 `null`）。建议 **v2 建底、v1 校准**。

### 2.2 期末考试 `GET /v1/rt/teaching_info/absent_examinfo`

```
examDate 考试日期 · examStartTime/examEndTime 起止 · roomName 考场
courseName 课程 · teacherStr 任课教师 · examType 1期末/2补缓考
examSituation 1正常/2缓考/3无资格/4免试 · weekNumber 第几周 · weekDay 星期
```

一条记录 = 一条完整待办（时间、地点、课程、教师全齐）。**这是"自动生成待办"最有说服力的演示素材**，比从通知正文里抽时间可靠一个数量级。

### 2.3 教务通知 `GET /v1/rt/onetongji/msg_list` + `msg_detail`

```
title 标题 · content HTML 正文 · publishTime 发布时间
faceUserName 面向对象（如"全校"）· commonAttachmentList 附件
startTime/endTime 通知有效期 · topStatus 置顶 · marReadStatus 已读
```

**两个必须先弄清的语义问题**：

1. 这个接口**确实没有参数**——不只是文档示例省略，官方目录里它的 `parameters` 也是 `null`。也就是说它不按用户区分，返回的极可能是**全校通知**。设计上应做成"全局拉一次 → 按 `faceUserName`（全校/学院/年级）过滤后展示"，而不是"每个用户各拉一次"。
2. `startTime`/`endTime` 是"通知展示有效期"，不是"办理截止时间"——**不能当截止时间用**，截止时间仍要从 `content` 正文里抽。

> **调用链提示**：`absent_examinfo` 与 `student_timetable` 都要求 `calendarId`（学期编号），而它要先由 `school_calendar_current_term_calendar`（客户端模式）拿到。所以"查考试"实际是两步：取当前学期 → 取考试。这个依赖要写进接口层的封装里，别让每个调用点自己拼。

### 2.4 毕业设计三节点（选题 / 中期 / 预答辩）

| 接口 | 关键字段 |
|---|---|
| `v1/dc/teaching_info_thesis_topic` | `topicTime` 选题时间 · `topicAddress` 地点 · `paperName` 论文名 |
| `v1/dc/teaching_info_midterm_assessment` | `assessTime` 考核时间 · `assessAddress` 地点 · `approvalStatusName` 审批状态 |
| `v1/dc/teaching_info_pre_defense` | `defenseDate` 预答辩时间 · `defenseAddr` 地点 · `teacherName` 导师 |

三类都是"某天某地要做什么"，天然是待办；且**大四学生最怕漏的就是这三个**，用户价值高于"某条通知改期"。

### 2.5 一网通办待办 `GET /v1/infra/task_center/task_list`

```
taskId · nodeName 当前节点 · taskStatus 1待处理/3已处理
taskCreated · instStatus · percent 进度 · appName 应用名
formUrl / formMobileUrl 办理入口 · thirdpartyName 任务名
```

这是"把学校已有的待办也收进来"的入口，可以做成"统一待办入口"的叙事——但注意 `appId` 默认只能查本系统推送的任务，查全量需单独授权（既已假定全权限，则可用）。

### 2.6 日程写入 `POST /v1/infra/calendar/person/create` —— 提醒的核心

```
eventTitle · startTime/endTime · eventAddr · eventDesc · linkUrl
eventRepeatType 0不重复/1每天/2每周/3每月第N天/4每年/5按月-周
eventRepeatData 间隔 · rangeType noEnd/endDate/numbered
remindTimes [分钟数组] 如 [15, 1440]
remindChannel INBOX/校园号/EMAIL/SMS/QYWECHAT/DINGTALK/WeChatService/WELINK
deadline · userId
```

**这一个接口就覆盖了 F4 的大部分需求**：重复规则（每周课）、提前量（多档）、渠道（站内/邮件/企业微信/短信）、截止时间。配套还有 `calendar/list`、`detail`、`update`、`delete`，可以做到"写入→回读→改期→撤回"的完整生命周期。

**架构含义**：R3（提醒任务丢失）从"要靠自建调度器 + 落库 + 补扫"变成"**把投递外包给平台**"。自建调度器降级为兜底（离线演示、平台不可用时），实现量和故障面都大幅下降。

### 2.7 推送渠道对照

| 渠道 | 接口 | 能力 | 约束 |
|---|---|---|---|
| 邮件 | `infra/notification/email` | 按学工号群发 | 全校共享 1000 封/15min、1 万/天；发件人固定"移动校园" |
| 企业微信 | `infra/notification/wecom` | 按学号，支持 `time` 定时 | 仅客户端模式 |
| 微信模板消息 | `infra/notification/mp` | **TDL 待办 / EN 考试 / JML 作业 / JDS 作业到期** | 用户需关注公众号；单个中间主内容 ≤20 字 |
| 短信 | `infra/notification/sms` | 按学号发送，支持 `time` 定时 | 文档未公开额度 |
| 日程 | `infra/calendar/*` | 多档提醒 + 重复 | 需用户开通校园号 |

模板消息的四种类型（TDL/EN/JML/JDS）几乎就是本项目的领域模型——**"待办""考试""作业""作业到期"**，可以直接对应 `TodoItem.category`。这条如果能用，`category` 字段的设计就等于有了官方参照。

### 2.8 其他可用但优先级低的数据

| 数据 | 接口 | 用途 | 局限 |
|---|---|---|---|
| 图书借阅明细 | `v2/dc/lib_lend_info_all` | 催还提醒 | 只有 `asbackDate` 催还日，**没有应还日** |
| 卓越星活动 | `rt/student_work_info/star/activity/page_all` | 活动报名 | 有活动起止/名额/报名人数，**未见报名截止字段** |
| 实习课程 | `dc/teaching_info_internship_course_scheduling` | 实习起止 | `courseDateStart/End` 可用 |
| 教学评价 | `dc/teaching_evaluation_course_evaluation` | — | 只有评价结果，**没有评教开放/截止时间** |
| 四六级/成绩 | `rt/onetongji/cet_score` 等 | — | 与待办无关，不建议纳入 |

## 3. 待办来源全景：7 类结构化 + 2 类文本（v2 的核心资产）

待办如果只靠"从通知里抽截止时间"，可靠性受文本质量限制。拿到权限后，顺序应该反过来：

| # | 来源 | 触发 | 待办内容 | 可靠性 |
|---|---|---|---|---|
| 1 | 期末考试 | 排考发布 | "12-30 13:30 材料科学基础2 · 博楼B110" | 高（结构化） |
| 2 | 补缓考 | 排考发布 | 同上，`examType=2` | 高 |
| 3 | 课表 | 学期开始 | "每周三 3-4 节 数据结构 · 嘉定A301" | 高（重复日程） |
| 4 | 毕业设计节点 | 选题/中期/预答辩 | "11-28 14:00 中期考核 · 学院会议室" | 高 |
| 5 | 实习课程 | 排课发布 | "7-04 至 7-15 数据结构课程设计" | 高 |
| 6 | 一网通办待办 | 用户授权 | 导入已有待办 + 办理入口 | 高 |
| 7 | 图书催还 | 逾期 | "《算法导论》已催还" | 中（无应还日） |
| 8 | 教务通知 | 新通知 | 抽取"9 月 27 日前提交材料" | 中（需抽取 + 人工确认） |
| 9 | 官网公告 / GitHub / 手动导入 | 新内容 | 同上 | 中 |

**产品含义**：把 1–7 做成"自动生成、无需确认"（结构化数据不会错；图书那条因缺应还日，降为"提示"），把 8–9 做成"草稿 + 用户确认"。这样"待办要人工改多少"这个验收指标会好看很多，也符合原文档"系统只生成草稿，不代替用户确认"的保守立场——**对结构化源可以更进一步，对文本源保持草稿**。

## 4. 5 个硬缺口

### 4.1 没有作业接口 🔴

237 个接口里"作业"命中 0 个。作业类待办只能来自：通知正文提到作业、或用户手动导入。**建议把文稿里的"新作业"改成"通知中提及的作业要求"**，并在演示时明确"作业提交不在本期范围"（原文档已经把"学习管理"砍掉了，这条要一致）。

### 4.2 官网没有 RSS，且部分正文是 PDF 图片 🔴 / 🟡

- 4 个站点 × 4 条常见 feed 路径全 404 → 通用 RSS 阅读器方案不成立，只能写站点适配器
- 本科生院：HTML 正文（412 字，可直接抽取）
- 计算机学院：正文是 **PDF 转图片**（`vsb_pdf_image_data`，可见文本仅 254 字）

**PDF 图片这一条现在有解了**：既然 OCR 接口可用，只要能拿到 PDF 原文件地址，就可以走 `file2md`。需要验证的是"图片序列背后有没有可下载的 PDF"。若没有，则只能对图片做 OCR，成本上升。

### 4.3 校历接口故障 🔴

`GET /v1/rt/onetongji/calendar` 恒返回业务码 **A07500**（"数据库中暑假的开始结束时间缺失"），4 个时间区间全一样。

- 能用的是 `teaching_info/semester`（匿名，66 个学期，含 `beginDay`/`endDay`/`examWeekStart`/`examWeekEnd`）→ **周次换算没问题**
- 不能用的是节假日/调休 → **"截止日遇节假日顺延"做不了**，建议从需求里删掉

### 4.4 OCR 只收公网 URL 🟡

`POST /v1/ai/tools/file2md/task` 的入参是 `file_url`，不是二进制。用户刚拍的截图不能直接喂。

三个选项：① 自建可公网读的对象存储；② 本地 OCR（PaddleOCR）或多模态模型；③ 截图只存图、用户手填。**建议 ②**，离线可控，也不依赖外网。

### 4.5 提醒准点率的验收路径 🟡

日程接口的 `remindTimes` 是"开始前 N 分钟"，`notification/wecom` 的 `time` 是"定时发送"。两者都由平台侧调度，准点率以本地调度路径验收。

NFR-3 要求 ±60s。**建议**：主路径用平台日程（可靠性高），同时在本地留一个轻量调度器做"平台失败时的兜底"，验收时用本地调度器证明 ±60s，用平台渠道证明"多端可达"。两者分开论证，比混在一起更稳。

## 5. 架构建议（基于全权限前提）

### 5.1 鉴权：能用授权码就用授权码

235 个文档页的分布：**22 匿名 / 80 仅客户端 / 124 客户端+授权码 / 1 授权码优先 / 8 未标注**。

仅客户端模式的接口（教务通知、期末考试、企业微信、卓越星活动）入参是 `userId`，意味着**应用可以查任意学号**。全权限之后这个风险不是消失了，而是变大了——答辩时"你们的系统能不能查别人的课表"是一个必问项。

**建议**：
- 支持授权码模式的接口（课表、日程、任务中心、通知推送）→ 一律用**用户登录后的 token**，`userId` 从 token 取，绝不从前端传
- 仅客户端模式的接口 → 后端只允许用"当前登录用户"的学号调用，并在代码层做一次断言 + 审计日志
- 把这条写进设计文档的"安全设计"一节，正好呼应 NFR-4

### 5.2 同步策略：DC 批量建底 + RT 实时校准

- DC 接口支持**不传参批量拉取**：每次固定 1000 条，用 `sinceId` 游标翻页；增量用 `sinceUpdateTime`
- RT 接口按 `userId` 单查，实时但字段少

**不要做全校预拉**：4 万学生 × 10 门课 = 40 万条，按 50 r/s 约 8 秒能拉完，但把全校课表落库是明显的合规问题。建议：**只对已授权用户按需拉取 + 本地缓存（TTL 1 天）**，用户登录时后台刷新。

### 5.3 幂等：用业务主键，不要用内容哈希

全权限后每个源都有稳定业务主键：考试 `examInfoId`、课表 `id`、通知 `id`、活动 `id`、待办 `taskId`。**NFR-2 直接变成 `UNIQUE(source, external_id)`**，比内容指纹更可靠（内容会改，主键不会）。

内容哈希仍然保留，但用途变成"**检测改期/撤回**"（同一主键、哈希变化 → 生成核对提示），而不是去重。这个分工更清晰。

### 5.4 待办与日程的双向映射

```
TodoItem --(create)--> 日程(person/create, linkUrl=本系统待办URL)
TodoItem --(update)--> 日程(person/update)
TodoItem --(delete)--> 日程(calendar/delete)
```

`linkUrl` 带上本系统待办地址，用户从日程点回系统；`eventDesc` 放来源与原文链接。这样"提醒"在用户侧是原生日历/校园号，在系统侧仍可编辑。

### 5.5 限流与超时预算

- 50 次/秒/应用/IP/并发；网关超时 60s；token 7200s
- 单用户首屏如果串行调 6 个接口（按每接口 300ms 估），最坏 ≈ 2s，会压线 NFR-1（P95 ≤1.5s）→ **必须并发拉取 + 本地缓存**，不要每次登录全量拉

## 6. 增量与里程碑（全权限版）

前提变了，v0.1 可以更激进——**第一版就接校内数据**，因为它比抓网页更可靠。

| 增量 | 目标 | 交付内容 | 演示重点 |
|---|---|---|---|
| **v0.1** | 校内数据 → 一条流 | 学校 OAuth 登录、课表/考试/教务通知拉取、通知流、去重、原文跳转 | 登录后 10 秒内看到"本周考试 + 本周课表 + 最新教务通知" |
| **v0.2** | 结构化待办 → 提醒 | 7 类结构化待办（考试/补缓考/课表/毕设/实习/待办导入/图书催还）+ 通知抽取待办、草稿确认、日程写入、提醒渠道、改期提示 | 现场造一条考试安排 → 日程里出现 → 手机收到提醒 |
| **v0.3** | 资料复用 + 管理面 | 收藏/标签/搜索、班委发布与阅读统计、管理员源与任务监控、RBAC、越权 403 | 双账号越权演示 + 后台源健康度 |

**保留一条降级链**（不是主线，但别删）：官网适配器 + GitHub + 手动导入。它既是"审批之外的兜底"，也是 v0.1 演示"多源"的素材——纯校内数据讲不出"聚合"的故事。

## 7. 剩余风险（技术类，非审批类）

| 编号 | 风险 | 影响 | 应对 |
|---|---|---|---|
| T1 | 教务通知接口无任何参数（`parameters=null`） | 拿到的是全校通知，数据量与受众过滤要自己处理 | 全局拉取 + 按 `faceUserName` 过滤；入库时记录受众范围 |
| T2 | DC 接口非实时（T+1） | 课表/考试变更延迟 | DC 建底 + RT 校准；UI 标注数据时间 |
| T3 | 校历 A07500 | 节假日顺延不可用 | 删需求或自建节假日表 |
| T4 | 官网正文 PDF 图片 | 该源不做文本抽取 | 找 PDF 原文件走 OCR；或该源只展示原文 |
| T5 | 平台提醒精度由平台侧调度决定 | NFR-3 的验收口径需固定 | 以本地调度路径验收，平台渠道证明多端可达 |

| T7 | 邮件额度全校共享 | 高峰期限流 | 主用日程/站内，邮件做补充 |

## 8. 接口语义与设计假设

以下是把接口文档读成实现约定时定下的假设，v0.1 联调时按此实现：

1. `msg_list` 无参数 → 按"全校通知 + 按 `faceUserName` 过滤"处理；`startTime`/`endTime` 视为展示有效期
2. 课表以 `v2/dc` 建底、`v1/rt` 校准；`delInd='D'` 视为退课，从周视图移除、保留历史
3. `examStatus=1`（未排考场）时考场字段留空，待办只显示时间与课程
4. 日程提醒按 `remindTimes` 配多档提前量，`remindChannel` 每次配一个渠道
5. 微信模板消息按 TDL（待办）、EN（考试）两类使用
6. `task_list` 按 `appId` 限定本系统推送的任务
7. 批量接口以 `sinceId` 做全量游标、`sinceUpdateTime` 做增量
8. `lordofthering` 属平台内部 scope，应用侧不申请、不依赖

## 11. 探测口径与方法

- **接口层**：以官方目录（`get_api_list`，237 条）与 235 个文档页为基准，逐条记录方法、地址、授权模式、参数与 scope
- **鉴权**：用文档公开的演示凭证取 token，再分别以"无 token / 错误 scope"调用业务接口，观察 401 与 403 的边界
- **数据面**：对两个匿名业务接口（学期、校历）直接取数；其余接口以文档返回参数表为准
- **网页源**：对 4 个站点 × 4 条常见 feed 路径做 RSS 探测；对本科生院与计算机学院的通知列表、详情页做解析验证
- **第三方**：GitHub 公开 API 做 ETag 条件请求与配额读取
- **环境**：本机公网出口（非校园网），2026-11-20；脚本见 `probe/`，结果见 `probe/probe_result.json`
