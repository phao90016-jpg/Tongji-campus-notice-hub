## 1. 项目基本信息

| 项 | 内容 |
|---|---|
| 项目名称 | 校园信息聚合与待办提醒系统 |
| 仓库 | campus-notice-hub |
| 课程 | 软件工程课程设计（CST3619 / 420146） |
| 团队规模 | 4–5 人（待填） |
| 立项日期 | 待填 |

## 2. 项目目标

把分散在多个平台的校园通知汇总为一个入口，自动整理为可核对的待办并按时提醒，
降低学生漏看通知与错过截止时间的概率。

**可度量的成功标准**

| 编号 | 标准 | 验证方式 |
|---|---|---|
| G1 | 订阅 2 个源后 10 秒内可在通知流看到汇总结果 | v0.1 演示 |
| G2 | 同一通知重复抓取 10 次仅入库 1 条 | 自动化测试（NFR-2） |
| G3 | 提醒在设定提前量 ±60s 内送达 | v0.2 现场演示（NFR-3） |
| G4 | 越权访问他人待办返回 403 | 双账号交叉请求（NFR-4） |
| G5 | 三个增量各有一个可运行版本并打 Release | GitHub Releases |

## 3. 范围

**纳入本期**

- 多源接入（RSS / GitHub 公开 API / 手动导入）
- 通知去重、归类、截止时间提取
- 待办草稿生成、确认与状态管理
- 提醒规则与推送（邮件 / Webhook）
- 收藏与标签、搜索
- 三类角色的权限控制与管理后台

**明确不做（本期）**

- 微信群 / QQ 群自动接收（无官方接口，改手动导入）
- 需登录的作业平台自动抓取
- 内容平台截图 OCR 自动识别（列 v0.3 可选）
- 课程成绩、作业提交等学习管理功能
- 支付类集成（需企业资质）

## 4. 过程模型选型论证

**结论：增量模型（Incremental），落实为两轮"计划—构造—测试—评审"迭代。**

选择理由：

1. **需求天然可分期。** 接入、归类、待办、提醒、归档之间是递进关系，
   每一期都能独立交付一个可演示版本，不需要等全部做完才能验收。
2. **与课程的 Milestone / Release 要求一致。** 要求每增量打 `v0.1/v0.2/v0.3` 并绑定 Milestone，
   增量模型天然对位。
3. **风险集中且可隔离。** 主要技术风险在接入适配层与提醒调度（R1、R3），
   用适配器隔离后，单个源出问题不阻塞整体交付。
4. **反馈周期短。** 每次课都是检查点，增量交付让教师的点评能直接落到下一期。

**不选其他模型的原因**

| 候选 | 结论 |
|---|---|
| 瀑布 | 需求会随源类型与提取规则变化，且过程中没有可演示的中间版本 |
| 螺旋 | 风险已识别且集中，不必每轮重做完整风险分析，成本高于收益 |
| 统一过程 UP | 用例驱动与迭代增量的思想采纳，但四阶段文档负担与 17 学时检查点不匹配 |
| 敏捷 / Scrum | 采纳看板、Issue 驱动、CI、迭代回顾等实践；不套用完整 Scrum 仪式——4–5 人、8 次课，仪式成本高于收益 |

## 7. 风险登记册

| 编号 | 风险 | 影响 | 应对 | 责任人 | 状态 |
|---|---|---|---|---|---|
| R1 | 信息源页面结构变化导致解析失败 | 该源通知断流 | 适配器隔离；健康检查；连续失败降级手动导入 | 开发 | 监控中 |
| R2 | 截止时间提取不准确 | 待办时间错误 | 规则优先；一律生成草稿由用户确认 | 需求 / 开发 | 监控中 |
| R3 | 提醒任务丢失 | 漏提醒 | 任务落库 + 幂等消费 + 启动补扫 | 开发 | 监控中 |
| R4 | 重复通知与改期识别错误 | 待办重复 / 沿用旧时间 | 内容指纹去重；改期只提示不覆盖 | 开发 | 监控中 |
| R5 | 第三方平台接口政策变化 | 功能不可交付 | 已移出范围 | 项目经理 | 已关闭 |

> R1 与 R3 为本项目重点管理的技术风险点，每轮迭代复盘更新状态。

## 8. 变更管理

## 9. AI 使用约定

- 遵循五总则：验证而非信任、规格先行、人守关卡、为再生成而设计、护密合规
- 所有 AI 产出在 [../08-AI使用/AI使用台账.md](../08-AI使用/AI使用台账.md) 登记
- 架构决策、需求确认、合并放行三处必须由人签字
- 密钥、个人数据严禁进入提示词
