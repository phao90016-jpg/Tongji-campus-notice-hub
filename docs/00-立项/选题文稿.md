# 面向大学生的校园信息聚合与待办提醒系统

**一句话描述：**把分散在学校官网、课程平台、GitHub 和班级群里的通知汇总到一个入口，自动整理成可核对的待办并按时提醒——给同时跟多门课和多项校园事务的大学生用。

本组拟设计一款面向大学生的校园信息聚合与待办提醒系统，把分散在学校官网、课程平台、GitHub、竞赛官网和班级群里的信息汇集到一个入口。系统将通知整理成可核对、可修改的待办，并把学生在其他平台遇到的有用内容保存到相应课程或主题下，帮助学生少漏看通知、少错过截止时间，也能在需要时找回资料。本期聚焦“接入—归类—待办—提醒”主链路，不包含课程成绩管理与作业提交等学习管理功能。

## 一　选题背景与目标用户

大学生在完成作业、参加竞赛和处理校园事务时，往往要同时查看多个平台。群通知容易被后续消息淹没，作业或报名改期后容易沿用旧时间，分散在各平台的收藏也难以和手头的课程或项目关联。

目标用户以需要跟进多门课程和校园事务的本科生为主，也覆盖经常参与竞赛或学生组织工作的学生；次要用户为负责发布班级与组织通知的班委、学生组织干事，以及维护信息源的系统管理员。

## 二　核心功能

**多源订阅与新消息接收　**支持添加学校及学院官网、竞赛官网的 RSS 或公开栏目、GitHub 课程仓库等来源，在来源支持的范围内自动获取新公告、新作业和资料更新。班级群消息不作为自动接入来源，学生可通过转发、粘贴文本或分享链接手动导入，保证在无官方接口的情况下流程仍然完整。

**信息归类与摘要　**对收集到的内容去重，按课程、考试、竞赛、校园事务和学习资料等归类。提取适用对象、关键要求、截止时间和办理入口，并保留原文或来源链接，便于核对。

**自动生成可编辑待办　**从作业发布、考试报名、材料提交等通知中生成待办草稿。学生可以增删、修改事项和时间，确认后加入待办列表，并按进度管理。系统只生成草稿，不代替用户确认。

**新消息通知与截止提醒　**按用户偏好推送新消息，对已确认待办发送截止提醒。发现原通知改期或撤回时提示用户核对和更新，并保留用户已有的编辑，不覆盖人工修改结果。

**跨平台收藏与知识存储　**支持通过系统分享、粘贴链接、复制文本或上传截图导入其他平台上的有用内容。资料可添加备注、摘要和标签，关联课程、项目或竞赛，并通过搜索重新查找。

**发布者与管理员后台　**班委和学生组织干事可向所属班级或组织发布通知并查看阅读情况；管理员维护信息源清单、监控抓取任务、管理用户与角色。该后台支撑本项目的角色与权限控制。

## 三　典型使用场景

学生订阅竞赛官网后，系统发现新的竞赛公告，分别提取报名和材料提交的截止时间，生成两条待办。学生核对原文、修改提醒时间后确认。随后，课程群补充了校内审核要求，学生把该通知转发导入同一竞赛条目，补充一项待办。准备材料时，学生还可以把在其他平台看到的经验帖保存到该竞赛资料夹，方便后续查找。

## 四　范围收敛说明

立项讨论中本组识别到原设想存在“多源全覆盖”导致的范围过大风险，按“宁小勿大”的原则收敛如下。未收敛项列入后续版本，不进入本期验收范围。

| 原设想 | 本期处理 | 理由 |
|---|---|---|
| 微信群自动接收通知 | 移出自动接入，改为转发／粘贴／分享链接手动导入 | 个人微信无官方开放接口，第三方方案违反平台协议且有封号风险，验收结果不可控 |
| QQ 群自动接收通知 | 同上；仅保留机器人接收 @ 消息作为可选实验，不进验收 | 需群管理员授权，消息范围与时效不由我们控制 |
| 其他内容平台（如小红书）导入 | 保留手动导入（粘贴／分享／截图）；OCR 自动识别列为 v0.3 可选 | 无官方接口，OCR 准确率不可控 |
| 需登录的作业平台自动抓取 | 移出；仅做公开页面与 RSS 定时检查 | 涉及账号凭据托管与合规风险 |
| “学习管理”（课程、成绩、作业提交） | 砍掉，不列入本期 | 与信息聚合边界重叠，显著扩大范围 |
| GitHub 课程仓库更新 | 保留 | 有公开 REST API，无需授权，是天然集成点 |

## 五　用户角色与权限控制

系统设置三类主要角色，另有可选教师角色，满足不少于三种角色的要求。权限采用基于角色的访问控制（RBAC）叠加资源归属校验。

| 角色 | 主要职责 | 数据权限边界 |
|---|---|---|
| 学生（student） | 订阅信息源，管理自己的通知、待办与收藏 | 仅本人数据；他人待办与收藏不可读、不可写 |
| 班委／学生组织干事（publisher） | 向所属班级或组织发布通知，查看发布与阅读情况 | 仅本班／本组织范围；不可查看个人待办内容 |
| 系统管理员（admin） | 维护信息源清单与抓取任务，管理用户与角色 | 全局配置与源管理；审计仅记录元数据，不读取待办正文 |
| 助教／教师（可选，v0.3） | 发布课程通知，查看本课程待办完成率 | 仅本课程聚合统计，不读个人明细 |

权限实现要点：① 接口层按角色鉴权，前台接口与后台接口分离；② 数据层按归属（owner_id、class_id）过滤，越权请求统一返回 403 且不泄露资源是否存在；③ 所有管理操作写入审计日志；④ 第三方登录只用于身份认证，角色与权限由本系统独立维护。

## 八　技术风险与应对

立项阶段识别五项风险。R1 与 R3 作为本项目的重点技术风险点纳入风险登记册，每轮迭代复盘时更新状态，满足“至少识别并管理一个技术风险点”的要求。

| 编号 | 风险描述 | 影响 | 应对措施 |
|---|---|---|---|
| R1 | 信息源页面结构变化导致解析失败 | 该源通知断流 | 适配器隔离各源；每源独立健康检查；连续失败告警并自动降级为手动导入 |
| R2 | 截止时间自然语言提取不准确 | 待办时间错误，用户错过截止 | 规则优先；提取结果一律生成草稿由用户确认；错误样本进回归用例 |
| R3 | 提醒任务丢失（服务重启或任务堆积） | 漏提醒，核心价值受损 | 提醒任务落库、幂等消费、启动时补扫；单元测试覆盖重启场景 |
| R4 | 重复通知与改期识别错误 | 待办重复或沿用旧时间 | 内容指纹 + 源内唯一键去重；改期只提示不覆盖用户已有编辑 |
| R5 | 第三方平台接口政策变化（微信／QQ） | 相关功能不可交付 | 已移出本期范围，系统不依赖 |

## 十二　关键状态图

以下三个关键类的状态迁移用于行为建模，已超过“至少两个关键类的状态图”的要求。图形化源文件（Mermaid）将在需求建模单元随 models/state/ 目录入库。

**待办事项 TodoItem　**草稿 → 已确认 → 进行中 → 已完成；已确认或进行中可转已过期；草稿或已确认可转已取消。用户确认是唯一的“草稿 → 已确认”入口，系统不得自动确认。

**订阅源 Source　**待验证 → 正常 → 失效；正常或失效可转已暂停；已暂停经重新验证回到待验证。连续抓取失败三次由正常转失效，并触发降级为手动导入。

**通知记录 Notice　**新接收 → 已归类 → 已生成待办 → 已归档。改期检测命中时回到已归类并生成核对提示。

## 十三　过程模型选型论证

本项目选择增量模型（Incremental），并在课程的检查点节奏下落实为两轮“计划—构造—测试—评审”迭代。选择依据如下：

| 候选模型 | 适用场景 | 本项目结论 |
|---|---|---|
| 瀑布模型 | 需求稳定、一次性交付 | 不选：需求会随源类型与提取规则变化，且过程中没有可演示的中间版本 |
| 增量模型 | 需求可分期、每期都能交付可用版本 | 选：三个增量对应三个可演示里程碑与三次 Release，与课程 Milestone 要求一致 |
| 螺旋模型 | 风险高，且需要每轮完整的风险分析 | 不选：风险已识别且集中在接入适配层，不必每轮重做风险分析，成本高于收益 |
| 统一过程 UP | 用例驱动、四阶段、文档较重 | 不选：用例驱动与迭代增量的思想采纳，但四阶段的文档负担与 17 学时检查点节奏不匹配 |
| 敏捷／Scrum | 需求多变、团队自主、迭代节奏短 | 部分采纳：采用看板、Issue 驱动、CI、迭代回顾等实践；不套用完整 Scrum 仪式——4–5 人、8 次课的规模下，仪式成本高于收益 |

## 十四　可行性与工程设计价值

系统拟为不同来源设计独立的接入模块，将获取到的信息转换为统一的通知记录。公开网站可通过 RSS 或对指定栏目的定时检查获取更新，GitHub 可通过公开接口读取课程仓库的变动；需登录的作业平台本期不做自动接入，改由手动导入兜底。技术选型为 Vue 3 + FastAPI 的前后端分离架构，定时抓取与提醒调度采用进程内调度器，数据库在开发期使用 SQLite、部署期使用 PostgreSQL。

对暂时无法自动接入的来源，支持复制文本、分享链接或上传截图，使其仍可进入后续分类、摘要和待办流程。用户资料应按授权采集并支持删除，密钥与个人数据不进入代码仓库，也不进入提示词。

课题可围绕数据来源适配、重复通知合并、截止时间提取、待办状态管理及提醒调度展开需求分析、系统设计与测试。重点验证同一通知重复发布、多个截止时间并存、截止时间缺失及原通知改期等情况。

## 十五　预期成果与应用价值

预期形成一个可演示的系统原型和配套课程设计文档，展示从信息接入、归类和摘要，到待办确认、提醒与资料归档的完整过程。产品价值可通过学生试用验证，重点观察是否减少了反复查看多个平台的时间，以及待办提取结果需要多少人工修改。若有进一步推广机会，可在班级、课程或学生组织中试点，考察通知发布与变更提醒的使用频率。
