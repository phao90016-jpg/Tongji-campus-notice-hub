# 面向大学生的校园待办中心

**一句话描述：**把学校教务系统里本来就有的课表、考试、毕设节点和通知，连同官网公告、GitHub 仓库和手动导入的内容，汇成一个入口，直接生成可核对的待办，并按用户设定的提前量提醒——让同时跟多门课和多项校园事务的学生不再靠记忆和截图过日子。

本组拟设计一款面向同济大学本科生的校园待办中心。核心判断是：**学生漏事，主要不是因为没有聚合，而是因为关键时间点散落在教务系统的不同页面里，且没有任何一处会主动提醒。**因此系统以学校开放平台的结构化数据为主源——课表给"每周什么时候上课"，排考数据给"哪天几点在哪考试"，毕设流程给"什么时候中期考核"，一网通办给"哪些申请还卡在哪个节点"——把这些直接变成待办，再用学校日程服务与消息服务把提醒送到学生手机上。官网公告、GitHub 课程仓库、班级群转发内容作为补充源，进入同一条通知流。

本期聚焦"接入—归一—待办—提醒"主链路，不包含成绩管理、作业提交、选课等学习管理功能。

## 一　选题背景与目标用户

### 1.1 问题

在同济，一个典型的本科生要同时跟四类时间点：课程（每周固定上课）、考试（排考后才有确切时间地点）、毕业设计或实习（选题、中期、预答辩、实习起止）、校务流程（奖助学金申请、证明开具等一网通办事项）。这四类信息分属不同系统、不同页面，且**没有任何一个会在到期前主动找学生**。

现有做法是截图、设手机闹钟、在群里问"是不是这周五交"，代价是三件事：

1. **漏**——考试地点临时调整、毕设中期考核时间变更，学生按旧信息行动；
2. **重复劳动**——每学期初把课表手工敲进日历，考试周再敲一遍；
3. **找不回**——当时看到的经验帖、通知原文、老师发的材料，散在聊天记录里，要用时找不到。

### 1.2 目标用户

| 用户 | 典型场景 | 核心诉求 |
|---|---|---|
| **主要**：需要跟进多门课程与毕业流程的本科生（大二至大四） | 一学期 8–12 门课、期末 5–8 场考试、毕设三个节点 | 打开就知道"这周要做什么、哪天考试、哪个还没交" |
| 次要：班委与学生组织干事 | 向班级发布通知、统计谁没看 | 发布后知道阅读情况，不用在群里反复 @ |
| 次要：系统管理员（课程项目内由团队兼任） | 维护信息源、观察同步任务健康度 | 源失效时能第一时间发现并降级 |

## 二　数据来源与现有设施

本项目的功能点全部锚定在**已存在的接口与页面**上，不假设任何不存在的接口。下表是本项目实际使用的数据来源，字段取自接口文档的返回参数表。

| 数据 | 接口 / 页面 | 授权模式 | 关键字段 | 支撑功能 |
|---|---|---|---|---|
| 课表 | `GET /v2/dc/teaching_info/student_timetable` | 客户端 / 授权码 | `weekday`、`startUnit`、`endUnit`、`week`、`classroomName`、`courseName`、`teacherName`、`delInd` | 课程档案、周课表、上课待办 |
| 实时课表 | `GET /v1/rt/onetongji/student_timetable` | 客户端 / 授权码 | `courseCode`、`classTime`、`credits` | 课表校准 |
| 期末考试 | `GET /v1/rt/teaching_info/absent_examinfo` | 客户端 | `examDate`、`examStartTime`、`examEndTime`、`roomName`、`courseName`、`examStatus` | 考试待办 |
| 补缓考 | `GET /v1/rt/teaching_info/deferred_examinfo` | 客户端 | 同上，`examType=2` | 补缓考待办 |
| 教务通知 | `GET /v1/rt/onetongji/msg_list`、`msg_detail` | 客户端 | `title`、`content`（HTML）、`publishTime`、`faceUserName`、`commonAttachmentList` | 通知流、文本待办草稿 |
| 学年学期 | `GET /v1/rt/teaching_info/semester` | **匿名** | `semesterName`、`beginDay`、`endDay`、`examWeekStart`、`examWeekEnd` | 周次换算、学期切换 |
| 毕设选题 | `GET /v1/dc/teaching_info_thesis_topic` | 客户端 / 授权码 | `topicTime`、`topicAddress`、`paperName` | 毕设待办 |
| 中期考核 | `GET /v1/dc/teaching_info_midterm_assessment` | 客户端 / 授权码 | `assessTime`、`assessAddress`、`approvalStatusName` | 毕设待办 |
| 预答辩 | `GET /v1/dc/teaching_info_pre_defense` | 客户端 / 授权码 | `defenseDate`、`defenseAddr`、`teacherName` | 毕设待办 |
| 实习课程 | `GET /v1/dc/teaching_info_internship_course_scheduling` | 客户端 / 授权码 | `courseDateStart`、`courseDateEnd`、`practiceDays` | 实习待办 |
| 一网通办待办 | `GET /v1/infra/task_center/task_list` | 客户端 / 授权码 | `taskId`、`nodeName`、`taskStatus`、`formUrl` | 导入已有待办 |
| 个人日程 | `POST /v1/infra/calendar/person/create`（含 `update`/`delete`/`list`） | 客户端 / 授权码 | `eventRepeatType`、`remindTimes`、`remindChannel`、`linkUrl` | 提醒投递、重复上课提醒 |
| 消息推送 | `POST /v1/infra/notification/email`、`wecom`、`mp`、`sms` | 客户端（部分含授权码） | `userId`、`title`、`content`、`time` | 新消息与截止提醒 |
| 图书借阅 | `GET /v2/dc/lib_lend_info_all` | 客户端 / 授权码 | `title`、`lendDate`、`asbackDate`（催还日）、`retDate` | 催还提示（无应还日，仅提示） |
| 官网栏目 | 本科生院 `/30359/list.htm` 等 HTML 页面 | 无（公开页面） | 列表条目、`div.wp_articlecontent` 正文 | 公告通知 |
| GitHub 仓库 | `GET /api.github.com/repos/{owner}/{repo}/commits` | 公开 REST（ETag） | `sha`、`commit.message`、`commit.author.date` | 仓库更新通知 |
| 截图识别（可选） | `POST /v1/ai/tools/file2md/task` | 客户端 | `file_url` → Markdown | 截图/PDF 转文本 |

**三条必须写进设计文档的事实：**

1. **两个匿名接口，只有一个能用。**`teaching_info/semester` 返回 66 个学期，可直接用于周次换算；`onetongji/calendar`（校历）目前恒返回业务码 `A07500`（"数据库中暑假的开始结束时间缺失"），**不可依赖**。因此本期不做"截止日遇节假日顺延"。
2. **教务通知接口没有任何参数**（官方目录中 `parameters` 为 `null`），返回的是全校通知，需要按 `faceUserName` 做受众过滤；其 `startTime`/`endTime` 是展示有效期，**不是办理截止时间**，截止时间只能从正文抽取。
3. **学校没有作业接口。**237 个接口中"作业"命中 0 个，因此"作业截止"只能来自通知正文或手动导入，系统不承诺"自动同步作业"。

## 三　核心功能

系统功能分六组，共 21 项功能需求（FR）。每项均标注数据来源与验收口径。

### 3.1 校内数据接入与首次同步

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-1 | 统一身份认证登录 | 走学校 OAuth2 授权码模式（`kc_idp_hint=tjiam`），回调换 token，解析 `userid`（学工号）作为系统唯一身份；不新建密码体系 | 新用户首次登录 ≤3 次点击完成；同一学工号重复登录不产生第二个账号 |
| FR-2 | 首次登录同步 | 登录成功后异步触发五路同步（课表、考试、教务通知、毕设节点、一网通办待办），前端先出骨架屏，各路完成即填充 | 首屏 10s 内可用；单路失败不影响其他路，失败项显示"重试" |
| FR-3 | 课表同步与课程档案 | 按 `(学号, 学年, 学期)` 拉课表，展开为"课程 + 节次"两级；`delInd='D'` 的记录标记为已退课，从周课表移除但保留历史 | 退课后再同步，该课程从周视图消失、历史记录仍在；同一节次不重复入库 |
| FR-4 | 考试与补缓考同步 | 先取当前学期编号，再取考试与补缓考；`examStatus=1`（未排考场）时 `roomName` 为空，待办只显示时间与课程 | 每场考试生成一条待办，含日期、起止时间、考场、课程、任课教师 |
| FR-5 | 毕设与实习节点同步 | 拉取选题、中期考核、预答辩三类节点与实习课程起止日期，各自生成节点待办 | 三类节点各生成一条待办；时间或地点缺失时保留待办、该字段留空 |
| FR-6 | 教务通知同步 | 拉取全校通知，按 `faceUserName` 记录受众；正文 HTML 清洗后入库，附件单独登记 | 同一通知重复同步不重复入库；正文可读、附件可下载 |

### 3.2 补充源与手动导入

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-7 | 官网栏目适配器 | 每个源一份配置（列表页 URL、条目选择器、正文选择器、日期格式），适配器注册表按配置实例化；不写死站点 | 新增一个同类栏目只改配置、不改代码；单源连续失败 3 次自动降级为"仅手动导入"并告警 |
| FR-8 | GitHub 仓库订阅 | 订阅公开仓库，拉 `commits` 与 `releases`，带 `ETag` 条件请求，304 时不计新增 | 无更新时不产生新通知、不消耗配额；有更新时生成含提交信息的通知 |
| FR-9 | 手动导入 | 三种入口：粘贴文本、粘贴链接、上传截图（截图可留空文字，v0.3 再接 OCR）；生成 `origin=manual` 的通知 | 导入后立即出现在通知流，并可被后续归类与生成待办 |

### 3.3 统一通知流与归类

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-10 | 统一通知流 | 校内通知、官网公告、GitHub 更新、手动导入合并为一条时间线；支持按来源、类型、课程、未读筛选；游标分页 | 1000 条数据下首屏 P95 ≤1.5s；筛选条件组合后结果正确 |
| FR-11 | 归类与关联 | 按规则把通知归到课程（匹配课程名/课程号/教师名）与类型（考试、教务、竞赛、事务、资料）；匹配不中则归"未分类" | 含课程名的通知命中率 ≥90%（以 50 条真实通知为样本人工核对） |
| FR-12 | 改期与撤回检测 | 同一业务主键（`source + external_id`）内容哈希变化时，生成"原文已变更，请核对"提示，不覆盖用户已编辑的待办 | 改期后原待办保留用户修改，另生成一条核对提示；撤回的通知标灰不再提醒 |

### 3.4 待办生成与状态管理

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-13 | 结构化待办（自动确认） | 考试、补缓考、上课、毕设、实习、一网通办、图书催还七类由结构化数据直接生成，标记 `auto_confirmed=true`，无需人工确认 | 同步后待办条数 = 考试数 + 节点数 + 课程节次数（去重后），无重复、无遗漏 |
| FR-14 | 文本待办草稿（需确认） | 从通知正文抽取"事项 + 时间 + 办理入口"，生成草稿并保留原文高亮片段；用户确认后才进入待办列表 | 每条草稿可一键跳回原文对应段落；抽取失败时给"手动建待办"入口而不是报错 |
| FR-15 | 待办状态机 | 草稿→已确认→进行中→已完成；已确认/进行中可转已过期；草稿/已确认可转已取消；用户确认是"草稿→已确认"的唯一入口 | 非法迁移返回 409；每次迁移写状态日志（操作人、时间、前后状态） |

### 3.5 提醒与日程

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-16 | 提醒规则 | 用户可为每类待办设默认提前量（5/15/30/60/1440 分钟）与渠道（站内、邮件、企业微信、微信模板消息）；单条待办可覆盖默认 | 修改默认规则后，新生成待办按新规则执行，历史待办不受影响 |
| FR-17 | 日程同步与兜底调度 | 已确认待办写入学校日程（`person/create`，携带重复规则、`remindTimes`、`remindChannel`、`linkUrl` 回链）；同时本地落一条提醒任务，用于平台不可用时兜底与准点率验收 | 待办确认后 5s 内出现在校园号日程；本地调度在 ±60s 内投递成功 |

### 3.6 资料收藏与后台

| 编号 | 功能 | 具体行为 | 验收口径 |
|---|---|---|---|
| FR-18 | 收藏与检索 | 收藏文本/链接/截图，可加备注、标签、关联课程；全文检索覆盖标题、正文、备注 | 搜索 200ms 内返回；标签与课程可组合筛选 |
| FR-19 | 班级通知发布与阅读统计 | 班委向所属班级发布通知，记录阅读回执，给出阅读率 | 仅本班可见；阅读率 = 已读人数 / 班级人数 |
| FR-20 | 源与同步任务监控 | 管理员查看每个源的最近同步时间、成功/失败次数、健康度；可手动触发同步、暂停源 | 源连续失败 3 次在后台标红并触发降级；手动触发有审计记录 |
| FR-21 | 用户、角色与审计 | RBAC + 资源归属校验；管理操作写审计日志（仅元数据，不记待办正文） | 越权访问统一 403 且不泄露资源是否存在；审计可按操作人/对象检索 |

> 说明：上表 21 项 FR 与第十一节 33 个功能用例为"需求—用例"多对多关系，追溯矩阵在需求规约单元建立。

## 四　典型使用场景

**场景一：开学第一周。**学生首次用学校账号登录，系统在 10 秒内拉完课表、考试、通知与毕设节点。首页"本周"显示：周三 3–4 节《数据结构》嘉定 A301、周五 13:30《材料科学基础2》考试（博楼 B110）、一条"第四轮选课安排"通知。学生把上课提醒设为"提前 15 分钟"，系统按每周重复规则写入校园号日程，此后每周三自动提醒，无需再手工敲日历。

**场景二：考试周改考场。**排考数据更新，某场考试的 `roomName` 从"博楼 B110"变为"博楼 A205"。系统检测到同一 `examInfoId` 的内容哈希变化，保留学生已改过的提醒时间（提前 60 分钟），仅更新考场并生成一条"考场已变更，请核对"提示。

**场景三：毕设中期。**系统从中期考核接口拿到 `assessTime=2026-11-28 14:00`、`assessAddress=学院 314`，自动生成待办并标为"已确认"。学生补充一条子任务"打印 3 份中期报告"，并把该待办关联到"毕业设计"资料夹；准备材料时把看到的格式模板收藏进同一资料夹，之后用"中期"关键词一次搜到。

**场景四：班委发通知。**班委在后台向本班发布"周五交实验报告"，系统推送站内消息与微信模板消息（TDL 类型），后台显示阅读率 32/38，班委对未读的 6 人再发一次提醒。

## 五　范围与取舍说明

本期范围按"宁小勿大"原则确定，取舍如下，理由均以实测为准。

| 曾评估的方案 | 本期处理 | 理由 |
|---|---|---|
| 官网 RSS 订阅 | 不采用，改用站点 HTML 适配器 | 实测 4 个站点 × 4 条常见 feed 路径全部 404，同济站点不提供 RSS |
| 学院官网全覆盖 | 只做 1–2 个已验证栏目（本科生院文本源、计算机学院图片源二选一） | 两个学院是两套 CMS、正文形态不同（HTML / PDF 图片），适配器不可复用 |
| 微信群 / QQ 群自动接收 | 不采用，改用转发、粘贴、分享链接手动导入 | 个人微信无官方开放接口，第三方方案违反平台协议且有封号风险 |
| 需登录的作业平台自动抓取 | 不采用；学校也没有作业接口（237 个接口中"作业"命中 0） | 涉及凭据托管与合规风险，且无接口可用 |
| 截图 OCR 自动识别 | 本期用手动导入，OCR 列为 v0.3 可选 | 学校 OCR 接口只收公网 `file_url`，不能直接传图 |
| 节假日顺延 | 不列入本期 | 校历接口恒返回 `A07500`，没有可信的节假日数据 |
| 图书到期提醒 | 只做"催还提示" | 借阅接口只有催还日 `asbackDate`，没有应还日 |
| 成绩、选课、作业提交等学习管理 | 不做 | 与信息聚合边界重叠，显著扩大范围 |

## 六　用户角色与权限控制

系统设置三类主要角色，另有可选教师角色，满足不少于三种角色的要求。权限采用基于角色的访问控制（RBAC）叠加资源归属校验。

| 角色 | 主要职责 | 数据权限边界 |
|---|---|---|
| 学生（student） | 查看通知与待办、管理自己的提醒与收藏 | 仅本人数据；他人待办与收藏不可读、不可写 |
| 班委／学生组织干事（publisher） | 向所属班级发布通知，查看阅读情况 | 仅本班／本组织范围；不可查看个人待办内容 |
| 系统管理员（admin） | 维护信息源与同步任务、管理用户与角色 | 全局配置与源管理；审计仅记录元数据，不读取待办正文 |
| 助教／教师（可选，v0.3） | 发布课程通知，查看本课程待办完成率 | 仅本课程聚合统计，不读个人明细 |

权限实现要点：

1. 接口层按角色鉴权，前台接口与后台接口分离，后台接口不暴露给前端路由；
2. 数据层按归属（`owner_id`、`class_id`）过滤，越权请求统一返回 403 且不泄露资源是否存在；
3. **校内数据接口的调用约束**：支持授权码模式的接口一律用"当前登录用户 token"调用，`userId` 从 token 取，不接受前端传入；仅客户端模式的接口（考试、教务通知、企业微信）由后端以应用身份调用，但入参 `userId` 必须等于当前登录用户，并在代码层断言 + 写审计日志；
4. 所有管理操作写入审计日志；
5. 第三方登录只用于身份认证，角色与权限由本系统独立维护。

## 九　技术风险与应对

立项阶段识别十项风险。R1 与 R3 作为重点技术风险点纳入风险登记册，每轮迭代复盘时更新状态。

| 编号 | 风险描述 | 影响 | 应对措施 |
|---|---|---|---|
| R1 | 官网页面结构变化或站点改版导致解析失败 | 该源通知断流 | 适配器隔离各源；配置化选择器；每源独立健康检查；连续失败 3 次降级为手动导入 |
| R2 | 文本源截止时间抽取不准确 | 待办时间错误 | 结构化源直接给时间不抽取；文本源一律草稿 + 原文高亮 + 用户确认；错误样本进回归集 |
| R3 | 提醒丢失（服务重启、任务堆积、平台不可用） | 漏提醒，核心价值受损 | 双路径：平台日程投递 + 本地任务落库（幂等消费、启动补扫）；单测覆盖重启场景 |

| R5 | 学校接口变更、下线或字段调整 | 相关功能不可用 | 接口层统一封装 + 契约测试；字段缺失时降级展示而非抛错；保留手动导入兜底 |
| R6 | 批量（DC）接口与实时（RT）接口数据口径不一致 | 同一待办出现两个时间 | 以 DC 建底、RT 校准；冲突时以 RT 为准并在 UI 标注数据时间 |
| R7 | 仅客户端模式接口被滥用为"查任意学号" | 合规与答辩风险 | `userId` 只取当前登录用户；代码层断言 + 审计；设计文档显式登记例外 |
| R8 | 校历接口不可用（`A07500`） | 节假日顺延缺少可信数据 | 本期不做顺延；周次换算改用学期接口 |
| R9 | 官网正文为 PDF 图片 | 该源不做文本抽取 | 该源只做原文展示；或取 PDF 原文件走 OCR（v0.3） |
| R10 | GitHub 未授权配额 60 次/小时/IP 被多用户挤占 | 仓库更新延迟 | 配 Token / GitHub App；ETag 缓存；失败退避 |

## 十三　关键状态图

以下四个关键类的状态迁移用于行为建模，超过"至少两个关键类的状态图"的要求。图形化源文件（Mermaid）在需求建模单元随 `models/state/` 目录入库。

**待办事项 TodoItem**　草稿 → 已确认 → 进行中 → 已完成；已确认或进行中可转已过期；草稿或已确认可转已取消。结构化来源生成的待办直接进入"已确认"（`auto_confirmed=true`），文本来源必须经用户确认。用户确认是"草稿 → 已确认"的唯一人工入口。

**订阅源 Source**　新建 → 正常 → 失效；正常或失效可转已暂停；已暂停经重新校验回到新建。连续同步失败三次由正常转失效，并降级为手动导入。

**通知记录 Notice**　新接收 → 已归类 → 已生成待办 → 已归档；改期检测命中时回到已归类并生成核对提示；撤回时进入已撤回（标灰、不删除）。

**提醒任务 ReminderTask**　待投递 → 投递中 → 已送达 / 失败；失败按退避重试，超过 3 次转人工排查；服务启动时对"待投递且计划时间已过"的任务补扫。

## 十四　过程模型选型论证

本项目选择增量模型（Incremental），并在课程的检查点节奏下落实为两轮"计划—构造—测试—评审"迭代。选择依据如下：

| 候选模型 | 适用场景 | 本项目结论 |
|---|---|---|
| 瀑布模型 | 需求稳定、一次性交付 | 不选：数据源字段与接口策略会随实测调整，且过程中需要可演示的中间版本 |
| 增量模型 | 需求可分期、每期都能交付可用版本 | 选：三个增量对应三个可演示里程碑与三次 Release，与课程 Milestone 要求一致 |
| 螺旋模型 | 风险高，且需要每轮完整的风险分析 | 不选：风险已识别且集中在接入层与提醒链路，不必每轮重做风险分析 |
| 统一过程 UP | 用例驱动、四阶段、文档较重 | 不选：采纳用例驱动与迭代增量思想，但四阶段的文档负担与 17 学时检查点节奏不匹配 |
| 敏捷／Scrum | 需求多变、团队自主、迭代节奏短 | 部分采纳：采用看板、Issue 驱动、CI、迭代回顾；不套用完整 Scrum 仪式——4–5 人、8 次课的规模下仪式成本高于收益 |

## 十五　可行性与工程设计价值

### 15.1 已完成的可行性探测

立项阶段对全部数据来源做了实测（探测脚本与结果随仓库 `probe/` 目录入库），关键结论：

- 开放平台共 **235 个接口文档页**，其中 **22 个匿名**、**80 个仅客户端模式**、**124 个支持客户端+授权码**；
- 用文档公开的演示凭证取 token 成功（**53ms**），调用课表接口返回 **403**、不带 token 返回 **401**，证明授权按接口 scope 逐项生效；
- 学年学期接口匿名可用，返回 **66 个学期**，含考试周起止；校历接口恒返回 **A07500**，不可用；
- 官网 4 个站点 × 4 条常见 feed 路径全部 404（**无 RSS**）；本科生院通知列表 9 条、正文 412 字可直接解析，两次抓取内容指纹一致；计算机学院正文为 **PDF 转图片**，需 OCR；
- GitHub 公开 API 可用，`ETag` 条件请求返回 **304**，未授权配额 60 次/小时/IP。

### 15.2 工程设计价值

系统拟为每类数据源设计独立适配器，把外部结构差异隔离在适配器内，统一转换为 `Notice`、`ExamEvent`、`CourseSession` 等内部分析类。技术选型为 Vue 3 + FastAPI 前后端分离，开发期 SQLite、部署期 PostgreSQL，同步与提醒采用进程内调度 + 任务落库。

可围绕以下问题展开需求分析、系统设计与测试，且都能造出可断言的用例：

- **多源归一**：同一场考试既出现在排考数据、又出现在教务通知里，如何去重与合并；
- **幂等同步**：同一批数据重复拉取 5 次，如何保证只有一份；
- **时间口径**：DC 批量接口与 RT 实时接口给出不同考场，以谁为准；
- **提醒可靠性**：平台日程与本地调度双路径，如何保证不漏且不重复；
- **越权边界**：仅客户端模式接口如何避免"查任意学号"；
- **降级路径**：源失效时如何在不打断主流程的前提下退回手动导入。

### 15.3 合规与数据最小化

校内数据按授权采集，只落库当前登录用户的明细；密钥、token、学工号不进入代码仓库，也不进入提示词；提供"删除我的数据"入口；审计日志只记元数据，不记待办正文。

## 十六　预期成果与应用价值

预期形成一个可演示的系统原型与配套课程设计文档，完整展示"登录 → 同步 → 归一 → 待办 → 提醒 → 归档"的链路。

产品价值可通过小范围试用验证，重点观察三个指标：

1. **漏事率**：试用两周内，学生错过的考试/节点数量（对照组用截图 + 闹钟）；
2. **人工修改量**：自动生成的待办中，用户修改过时间或标题的比例（结构化源应显著低于文本源）；
3. **回访频率**：学生主动打开系统的次数是否随通知量下降而稳定（说明它变成了"待办入口"而不是"又一个信息流"）。

若有推广机会，可在班级或学生组织中试点，考察通知发布与阅读统计的实际使用率。
