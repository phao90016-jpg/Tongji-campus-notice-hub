# ADR-0001 采用分层架构 + 适配器模式

> ⚠️ **选题已于 2026-11-20 升级到 v3**：主源改为校内结构化接口，登录改为学校统一身份认证，用例编号由 UC-01~26 调整为 UC-01~33。本文件仍按 v2 编写，编号与范围待按 v3 重写——进度与编号映射见 [变更说明-选题v3](../../00-立项/变更说明-选题v3.md)。

- **状态**：已接受
- **日期**：待填
- **决策人**：架构 / 设计工程师（人守关卡：架构决策须签字）

## 背景

系统需要接入多种异构信息源（RSS、GitHub API、手动导入），且未来可能新增。
风险登记册中 R1 指出：源页面结构变化会导致解析失败。若把各源解析逻辑散落在业务代码里，
一个源出问题会牵连整个抓取链路，且新增来源要改动多处。

## 决策

采用**前后端分离的分层架构**（表现层 / 接口层 / 应用层 / 领域层 / 接入层 / 基础设施），
并在接入层使用**适配器模式**：每个信息源实现统一的 `SourceAdapter` 接口
（`source_type`、`fetch`、`normalize`），上层只依赖统一的通知草稿。

## 备选方案

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 单一抓取函数 + if/else 分支 | 起步快 | 分支膨胀，单源故障牵连全局，难测试 | 否决 |
| 适配器模式 | 故障隔离，易扩展，可单独测试 | 初期多一层抽象 | **采纳** |
| 插件热加载 | 可动态扩展 | 复杂度高，课程项目不需要 | 否决 |

## 后果

**正面**
- 单源解析失败只影响该源，并可通过健康检查降级为手动导入（R1 应对）
- 新增来源只需新增适配器 + 注册，不改上层（可演进性）
- 每个适配器可独立单元测试，便于达到覆盖率要求

**负面**
- 需要维护统一的数据模型 `NoticeDraft`，字段设计要一次想清楚
- 抽象层带来少量样板代码
